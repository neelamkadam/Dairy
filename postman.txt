# Frontend Flow — CC / BMC / Routes / Dairy (VLC) / Shift Timings

Base URL examples assume the API root (same server as all `/web/*` endpoints).
All responses follow the usual shape: `{ success: true, data / message }` on success,
`{ success: false, message }` with HTTP 400 / 403 / 404 on errors.

---

## 1. The model in one picture

```
Admin web_user (is_admin = 1)
 └── registers CCs (Chilling Centers)          ids: 700001, 700002, ...
      └── registers BMCs under a CC            ids: 800001, 800002, ...
           └── registers Routes                ids: 900001, 900002, ...
                (a route can be under a BMC, a CC, or BOTH)
                └── Dairies (VLCs) — the actual data lives here.
                    Each dairy has OPTIONAL cc_id, bmc_id, route_id links
                    (any combination, or none at all).
```

Key rules:

- **CC, BMC and Route are registered like a dairy**: `name`, `villagename`, `address`, `ownername`.
  The generated id is returned by the create call and **is the real id** used everywhere
  (`cc_id: 700001`, `bmc_id: 800001`, `route_id: 900001`, each series counts up on its own).
- **CC and BMC also take a required `password`** at registration and **can log in** with
  their generated id as the username (section 5). Routes have no login.
- **BMC requires a CC** (`ccId`) at creation. A **Route** can take `bmcId`, `ccId`, or **both**.
- **The dairy (VLC) is the source of truth**: its `cc_id` / `bmc_id` / `route_id` columns say where
  it sits in the hierarchy. CC/BMC/Route are just collections of VLCs. All three links are optional.
- Only admins (`is_admin = 1`) can create / update / assign. All list & read endpoints accept
  a sub-user id too — the backend resolves their admin automatically.
- Assigning a **BMC or CC** to a sub-user implicitly brings everything under it;
  assigning a **route** brings just that route's VLCs.
- Shift timings are **not enforced by the backend** on the collection APIs — the frontend
  must gate the entry forms using the status endpoint (section 7).

## 2. Admin — registration screens (top-down order)

Build the screens so the admin registers top-down: CC first, then BMC, then Route, then dairies.

### CC screen

| Action | Call |
|---|---|
| Register | `POST /web/cc/create` `{ adminId, name, villagename, address, ownername, password (required) }` → returns `cc_id` (700001+) and `username` — **show these to the admin, they are the CC's login credentials** |
| List | `GET /web/cc/list/:userId` → rows include `bmc_count`, `route_count`, `vlc_count` |
| Update | `PUT /web/cc/update` `{ ccId, name, villagename, address, ownername, password? }` — include `password` only to change it |
| VLCs under it | `GET /web/cc/:ccId/vlcs` |
| Delete | `DELETE /web/cc/:ccId` → children are kept, their `cc_id` becomes null |

### BMC screen

| Action | Call |
|---|---|
| Register | `POST /web/bmc/create` `{ adminId, ccId (required), name, villagename, address, ownername, password (required) }` → returns `bmc_id` (800001+) and `username` — the BMC's login credentials |
| List | `GET /web/bmc/list/:userId` → rows include `cc_name`, `route_count`, `vlc_count` |
| Update | `PUT /web/bmc/update` `{ bmcId, ccId?, name, villagename, address, ownername, password? }` — send `ccId` to move it, `password` to change it, omit either to keep |
| VLCs under it | `GET /web/bmc/:bmcId/vlcs` |
| Delete | `DELETE /web/bmc/:bmcId` |

UI: the create form needs a CC dropdown (from the CC list call) — it's mandatory.

### Route screen

| Action | Call |
|---|---|
| Register | `POST /web/routes/create` `{ adminId, name, villagename, address, ownername, bmcId?, ccId?, vlcIds?: [dairy ids] }` → returns `route_id` (900001+) |
| List | `GET /web/routes/list/:userId` → each route has `bmc_name`, `cc_name`, `vlcs[]` |
| Update | `PUT /web/routes/update` `{ routeId, name, villagename, address, ownername, bmcId?, ccId? }` — **full replace**: an omitted/null parent is cleared, so always send the complete desired state |
| Edit VLCs | `PUT /web/routes/vlcs` `{ routeId, vlcIds: [...] }` — replaces the route's VLC membership (sets `dairy.route_id`; dairies dropped from the list are detached) |
| Read VLCs | `GET /web/routes/:routeId/vlcs` |
| Delete | `DELETE /web/routes/:routeId` |

UI: the create form can show **two** dropdowns — BMC and CC — either, both, or none can be picked.
`vlcIds` on create is a shortcut that links the selected dairies to the new route immediately.

### Dairy (VLC) registration — existing screen, extended

The existing dairy registration now accepts the three optional hierarchy links:

- Register: `POST /branch/create` — same body as before **plus optional** `cc_id`, `bmc_id`, `route_id`.
- Edit: `PUT /branch/updateDairydetails/:id` — partial update; for the three link fields:
  **send a value to link, send `null` to detach, omit the key to leave unchanged.**

UI: add three optional dropdowns (CC / BMC / Route) to the dairy form, filled from the list calls.

## 3. Admin — assignment screen

Pick a sub-user, then:

| Action | Call |
|---|---|
| Assign CC | `POST /web/cc/assign` `{ adminId, userId, ccId }` |
| Assign BMC | `POST /web/bmc/assign` `{ adminId, userId, bmcId }` |
| Assign Route | `POST /web/routes/assign` `{ adminId, userId, routeId }` |

## 4. Sub-user — login / scope bootstrap

After the existing `POST /web-users/login`, when the user is **not** an admin, make one call:

```
GET /web-users/assignments/:userId
```

Response shape:

```jsonc
{
  "success": true,
  "data": {
    "ccs": [ {
      "id": 700001, "name": "CC Dhule", "villagename": "...", "address": "...", "ownername": "...",
      "routes": [ { "id": 900001, "name": "Route 1",
                    "vlcs": [ { "dairy_id": 7, "name": "...", "branchname": "...", "villagename": "...",
                                "cc_id": 700001, "bmc_id": 800001, "route_id": 900001 } ] } ],
      "vlcs":   [ /* dairies linked DIRECTLY to this CC (dairy.cc_id) */ ]
    } ],
    "bmcs":   [ /* same shape: routes[] under the BMC + vlcs[] linked directly to it */ ],
    "routes": [ /* routes assigned DIRECTLY to the user, each with vlcs[] */ ]
  }
}
```

Build the sub-user's working scope from this:
**their VLCs = union of every `vlcs` array in the response** (routes under CCs/BMCs,
direct VLCs of CCs/BMCs, and directly assigned routes).
Use that set to filter dairy dropdowns, dashboards, entry screens, etc.

Admins skip this call — they own everything, use the `list/:userId` endpoints.

## 5. CC / BMC login — "dairies are their farmers"

A CC or BMC logs in with **its generated id as the username** plus the password set at
registration. One shared endpoint handles both — the id decides the type:

```
POST /web/cc/login        (identical endpoint also mounted at /web/bmc/login)
{ "username": "700001", "password": "secret123" }
```

Response:

```jsonc
{
  "success": true,
  "message": "Login successful",
  "type": "CC",                          // or "BMC" — auto-detected from the id
  "data": { "id": 700001, "name": "CC Dhule", "villagename": "...", "address": "...",
            "ownername": "...", "created_by": 1, ... },   // no password field
  "vlcs": [                              // the dairies under it — these ACT AS ITS FARMERS
    { "dairy_id": 7, "name": "VLC Sanjay Dairy", "branchname": "...", "ownername": "...",
      "villagename": "...", "address": "...", "active": 1,
      "cc_id": 700001, "bmc_id": 800001, "route_id": 900001 }
  ]
}
```

Frontend behaviour:

- Build the CC/BMC home screen exactly like the dairy screen builds its farmer list,
  but the rows are the `vlcs` from the login response.
- To refresh the list later without re-login: `GET /web/cc/:ccId/vlcs` or `GET /web/bmc/:bmcId/vlcs`.
- Which dairies appear is decided by the **dairy's own link columns**: a dairy shows under the
  CC whose id is in its `cc_id`, and under the BMC in its `bmc_id` (set at dairy registration
  or via dairy update).
- Wrong id/password → 401 "Invalid credentials". A CC/BMC created before passwords existed
  (password never set) → 401 "Login not enabled for this account. Set a password first." —
  fix it by having the admin set a password through the update endpoint.
- Routes cannot log in — there is no password on routes.

## 7. Shift timings (gates the entry forms)

### Settings screen (admin)

- Prefill: `GET /web/shift-timings/get/:userId` → `data` is the 4 times or `null` if never set.
- Save: `PUT /web/shift-timings/set`

```json
{ "adminId": 1,
  "morning_start": "06:00", "morning_end": "11:00",
  "evening_start": "16:00", "evening_end": "21:00" }
```

Rules: times are **IST**, `HH:MM` or `HH:MM:SS`; a shift's start & end must be sent together;
send both as `null` to make that shift unrestricted.

### Gating the collection entry UI (all users)

Before enabling any collection entry form:

```
GET /web/shift-timings/status/:userId
```

```jsonc
{
  "success": true,
  "data": {
    "current_time": "07:15:32",          // IST, from the server — do NOT use device time
    "timezone": "IST",
    "morning": { "start": "06:00:00", "end": "11:00:00", "configured": true,  "active": true  },
    "evening": { "start": null,       "end": null,       "configured": false, "active": true  },
    "allowed_shifts": ["Morning", "Evening"],
    "entry_allowed": true
  }
}
```

Frontend behaviour:

- `entry_allowed === false` → disable the whole entry form, show something like
  "Entries open at {morning.start} / {evening.start}".
- Otherwise limit the shift selector to `allowed_shifts`
  (inside the morning window only "Morning" may be submitted, etc.).
- A shift with `configured: false` is always `active: true` — no config means no restriction.
- Re-check on screen focus and around window boundaries (polling once a minute is fine).
  Remember: the backend does not reject out-of-window entries, so this UI gate is the enforcement.
